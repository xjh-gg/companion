# M5 小智固件可行性探索记录

> 阶段：M5（语音抽象接口层建立，未接真实硬件）
> 定位：**探索思路记录**，非实现结果。所有"可行性结论"均标注**待验证**，需要在小智固件/音频驱动真正跑通后确认。

## 1. 背景

Companion（ESP32-S3）M5 阶段目标是"语音对话"。硬件上已具备：
- 音频 Codec：**ES8388**（I2C 地址 0x10，I2S 数据接口），用于麦克风输入 + 喇叭输出；
- 音频通路：麦克风（输入）→ ES8388 ADC → ESP32-S3 I2S；ESP32-S3 I2S → ES8388 DAC → 喇叭（输出）。

软件上按"语音对话用 小智 AI 固件"做技术选型。**小智 = Xiaozhi ESP32 / 小智（xiaozhi-ce）开源项目**，是一套面向 ESP32 系列的 AI 语音助理固件（含触摸/唤醒词/流式语音对话/大模型接入等）。

本阶段仅建立 `voice.h` 抽象接口层（空实现），把"音频接入点"隔离出来；小智固件如何集成留作下一步探索。

## 2. 小智固件是什么、以何种形态运行（待验证）

小智是一个开源 AI 语音助手方案，对 ESP32 生态提供了**独立固件**支持（chromatic 的各种板型中均有 ESP32-S3 相关支持）。

接入形态通常有两种，需根据仓库资料核实（**待验证**，勿臆断）：

| 形态 | 说明 | 对本项目的适配度（待验证） |
| --- | --- | --- |
| **A. 独立固件（整机刷机）** | 小智作为完整固件整体烧录进 ESP32-S3，自带唤醒词、网络、扬声器播放链路 | 需用小智支持的板型模板；Custom（原子小智）可针对自研板改硬件/引脚配置。与本项目现有 M1–M4 应用（传感器/状态机/事件等）**冲突/不共存**，需评估是否"整机替换"。 |
| **B. SDK / 组件（库式集成）** | 把语音链路（唤醒、链路、编解码）作为组件/库嵌入本项目，与现有 main 应用共存 | 集成面更窄，但要与现有 FreeRTOS 任务、事件循环做共享/仲裁。**待验证小智是否提供可分离的音频库形态**（更可能是整机固件形态）。 |

> 目前更偏向"小智以独立固件形态存在，原子小智/Custom 板型便于针对自研 ESP32-S3 板改造"。因此**第一步应验证小智固件能在本板跑通**，再决定集成深度。

## 3. 接入所需前置（待验证）

无论哪种形态，接入都依赖以下能力（需在目标板实测）：

1. **ES8388 I2S 驱动**
   - I2S（PDM/TDM 或标准 I2S）时钟、采样率（AI 通常 16kHz/16bit 或更高）、DMA buffer 配置；
   - ES8388 的 I2C 寄存器初始化（ADC 输入增益、DAC 输出、左右声道、音量）。
2. **麦克风 + 喇叭接通**
   - 麦克风偏置/ADC 通路、喇叭 DAC 通路接线与增益校验。
3. **唤醒词（Wake Word）**
   - 本地脱机唤醒词（如 ESP-SR 的 WakeNet，支持自训练）**vs** 云端持续唤醒；
   - 本地唤醒对功耗/实时性更优，但消耗 Flash/RAM（ESP32-S3 需留意 PSRAM 是否启用）。
4. **网络 + 流式对话**
   - Wi-Fi 建链、音频流上传/下发、与大模型服务端（WebSocket/HTTP）的交互协议。

## 4. 与当前项目分层如何对接（基于 voice.h 抽象层）

当前项目已建立语音隔离层：

- `main/voice.h`：`voice_init / voice_session_start / voice_session_stop / voice_play / voice_record_start / voice_record_stop / voice_get_state`，含会话状态枚举 `voice_session_state_t` 与结束原因 `voice_end_reason_t`。
- `main/voice.c`：空实现，所有功能接口返回 `ESP_ERR_NOT_SUPPORTED`，状态恒为 `VOICE_IDLE`。

对接方式（待验证，需按实际形态落地）：

- **若采用独立固件（形态 A）**：很难与本项目共存，可能需要把 companion 的 M1–M4 功能决策为"保留 or 裁剪"，`voice.h` 仅作为边界；或者评估小智固件上再叠加 companion 逻辑。
- **若采用 SDK/组件（形态 B）**：把真实的播放/录音/会话实现填进 `voice.c`，保持接口不变，上层（状态机）无需改动即可切换到真实音频——这正是 M5 建立抽象层的核心目的（**接入点隔离**）。
- 状态机已有事件：`EVT_INTERACT_START` / `EVT_INTERACT_END`（M2 预留）——语音会话起止时可投递这两个事件，联动的迁移逻辑已在状态机内处理（M2 已实现），voice 层无需改状态机。

## 5. 风险项与备选思路（待验证）

| 风险 | 说明 | 思路 |
| --- | --- | --- |
| 小智固件源码集成难度大 | 多为整机固件，拆成组件成本高 | **先验证小智固件能在本板完整跑通**（刷机能唤醒、能对话、喇叭响、麦克风收），再决定集成深度。 |
| 与现有 M1–M4 应用共存冲突 | 传感器/状态机/事件架构与小智整机固件冲突 | 若不能共存，可采用"裁剪 companion 或裁剪小智"，优先保住语音对话为第一优先（如需 M5 目标）。 |
| ES8388 + 自研板的引脚适配 | 需按自研板改引脚/启用 PSRAM | 参照原子/其他 ES8388 样板型调整 circuitboard / app 配置（待验证）。 |
| 唤醒词资源占用 | 本地唤醒词吃 Flash/RAM | 确认 ESP32-S3 是否启用 PSRAM；必要时降级为按键触发会话（voice 层已支持 `voice_session_start`）。 |
| 服务端/账号依赖 | 云端对话需接入服务商与大模型 | 验证阶段可用小智官方默认服务跑通链路，再做深度定制。 |
| 备选方案 | 若小智集成不可行 | 自研最小语音链路：ESP-SR 本地唤醒 + I2S/ES8388 播放与录音 + 第三方 TTS/STT/LLM 接口，均从 `voice.h` 接入，接口不变。 |

## 7. 结论与验证路径

**结论**：语音对话采用"小智固件"技术选型成立，但**集成深度取决于小智固件能否与本项目共存**（待验证）。M5 已通过 `voice.h` 抽象层把音频接入点隔离，后续任何形态的实现都只需填写 `voice.c`，不改上层。

**建议验证路径**（由 Independent 到逼近生产）：
1. 先在小智支持的某块 ESP32-S3 样板/自研板上**整机刷小智固件**，验证唤醒、对话、喇叭/麦克风全链路可用；（关键里程碑，**待验证**）
2. 若可用且能接受裁剪：在整机固件上裁剪/融合 companion 的 M1–M4 需求，或评估共存方案；
3. 若不可共存：走备选自研最小语音链路，全部从 `voice.h` 接入；
4. 最终实现阶段：在 `voice.c` 填接 ES8388(I2S) + 语音链路，满足验收"构建通过 + 接入点隔离"。
