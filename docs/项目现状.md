## 3. 本次会话关键修复记录

### 3.1 串口首配 `fgets` 立即返回问题
- **现象**：USB-Serial/JTAG 作为主控制台时，复位后 host 串口需时间重新连接；直接 `fgets` 在 CDC 缓冲为空瞬间立即返回，导致首配整段被跳过。
- **修复**：`read_line` 改为循环短延时重试，直至读到非空行或等待窗口（120s）超时。见 [config.c](file:///d:\Projects\workspace\companion\main\config.c#L126-L149)。
- 首配提示与保存逻辑见 [config.c](file:///d:\Projects\workspace\companion\main\config.c#L159-L168) 与 [config.c](file:///d:\Projects\workspace\companion\main\config.c#L80-L92)。

### 3.2 AT24C02 写入失败根因与修复（tWR 时序）
- **现象**：`at24c02_write` 回读校验报 `ESP_ERR_INVALID_RESPONSE`（NACK），但读路径正常。
- **排查结论**：官方手册确认 DNESP32-S3 的 AT24C02 **WP 引脚接地**，写保护可排除；根因是**固定 5ms tWR 延时偶尔不足**——芯片内部编程周期结束前不响应 I2C，此刻回读即 NACK。
- **修复**：固定延时改为 **ACK 轮询**（每 10ms 回读一次，直至芯片重新 ACK 或 500ms 超时），持久化经实机验证**跨重启生效**。见 [at24c02.c](file:///d:\Projects\workspace\companion\components\BSP\AT24C02\at24c02.c#L33-L66)。

### 3.3 WiFi/MQTT 凭据运行时注入
- 主控制台切至 USB_SERIAL_JTAG；凭据经串口注入，仅存 AT24C02，未写入任何构建产物（已验证编译后固件无明文凭据）。
- **保存成功才重启**；若 EEPROM 暂不可写则保留内存凭据继续本次运行。见 [config.c](file:///d:\Projects\workspace\companion\main\config.c#L80-L92)。
- `wifi_manager` / `mqtt_manager` 均改为从 `config_get()` 读取 SSID/密码/broker URI。

### 3.4 暗光改为“仅记录、不报警”（方案 C）
- **行为**：环境光过暗不再触发 `STATE_ALARM`；`sensor_task` 不再投递 `EVT_DARK`，状态机即使收到也不会迁移。暗光不改变状态、LED、蜂鸣器与犯困计时，也不写 AT24C02。
- **判定**：进入阈值 50（`ALS_DARK_THRESHOLD`）、恢复阈值 60（`ALS_RECOVER_THRESHOLD`）、连续 3 次采样确认（`ALS_DEBOUNCE_COUNT`，采样周期约 50ms）；50~59 为迟滞带，维持当前判定，不反复打日志。
- **独立性**：PS 手靠近与 ALS 判定拆为两个独立 `if`，PS 持续过阈值不再遮挡 ALS 采样。
- **状态**：✅ 代码修改完成、✅ 构建通过（2026-10-21，`companion.bin` 0x1012d0，1,053,392 字节，31% 空闲）；✅ 实机重复遮挡/恢复响应通过（2026-10-21，见 3.5）；恢复阈值 60 仍未完成系统标定。

**本次三类前置**（此前 Advisor 指出否则播放必失败）：
1. **PSRAM**：`sdkconfig` 开启 `CONFIG_SPIRAM=y` + `CONFIG_SPIRAM_MODE_OCT=y`（板载 8MB Octal，N16R8/N8R8 类 WROOM）+ `CONFIG_SPIRAM_TYPE_AUTO=y` + `CONFIG_SPIRAM_SPEED_80M`；开机日志确认 `8177K PSRAM` 入堆。
2. **Flash 16MB**：`CONFIG_ESPTOOLPY_FLASHSIZE` = 16MB（bootloader 曾报 16MB>2MB 头冲突）；烧录用 `--flash-size 16MB`。
3. **分区放大**：`CONFIG_PARTITION_TABLE_SINGLE_APP_LARGE=y`（factory 1.5MB），避免加 codec 后 app 溢出（当前 app 约 936KB）。

**关键实现点**（参考 esp_codec_dev 1.6.2 实际源码）：
- ES8388 I2C 地址在 esp_codec_dev 界面上填 **8bit 形态 `0x20`**（底层 `addr>>1` → 总线 0x10），复用项目 I2C 总线句柄 `g_i2c_bus`（`audio_codec_i2c_cfg_t.bus_handle`）。
- I2S 用 `I2S_CHANNEL_DEFAULT_CONFIG(I2S_NUM_0, MASTER)` 全双工创建 TX/RX，并 `i2s_channel_init_std_mode` 设 `gpio_cfg{mclk=3,bclk=46,ws=9,dout=10,din=14}`；`esp_driver_i2s` 需加入 main 的 REQUIRES。
- `esp_codec_dev` 全双工下 rx 通道自动评为 slave（日志 `rx channel on I2S0 is switched from master to slave`），正常。
- codec 打开采样格式为 16kHz/16bit/双声道；MCLK = fs×256（4.096MHz）。

### 5.6 物理无声排查清单（2026-10-20，软件已证全绿，收敛为硬件）

日志显示 ES8388 Open OK、`esp_codec_dev_write` 返回 0、I2S 已启动。**已进一步做寄存器回读取证**：执行 `dump_es8388_regs`，确认 DAC 功率(0x04=0x3C)、DAC 静音位(0x19=0x00 已解静)、音量(0x1A/0x1B 非 0)、输出负载(0x26/0x27/0x2A)均正常；并在 open 后执行 `es8388_ensure_dac_output()` 强制写入"已知可出声"的 DAC 输出兜底（UNMUTE + DAC PWR + LOUT/ROUT 0dB）。**因此软件层可排除"DAC 残留静音/未使能"根因，无声收敛到 CRITICAL 时钟/功放硬件**。按优先级核查：
1. **MCLK 是否真实输出**：ESP32-S3 的 I2S MCLK 需 IOMUX 路由到 GPIO3；用示波器/逻辑分析仪量 GPIO3 是否出现 4.096MHz（fs×256）。若无系统时钟，codec 有 I2C 也无法 DAC 出音。
2. **SPK_EN_IO 是否真驱动功放**：`xl9555_pin_write(SPK_EN_IO,1)` 后万用表量功放使能脚电平，确认该 bit（XL9555 PORT0 bit2）确实对应喇叭功放使能；部分板型喇叭经耳机功放/PCM，需额外配置。
3. **音源/接线**：确认该板喇叭接在 ES8388 的 OUT1/OUT2（非外接耳机）；换更响/更长的正弦（如 2kHz、满幅、5s）排除音量与持续时间因素。
4. **I2S 数据格式对齐**：当前 16bit 双声道写入；若板子期望单声道/不同 slot，ES8388 会收到但可能静音输出——对照正点原子例程的 slot 配置核对。

> 注：软件寄存器回读已排除第 3 项"ES8388 DAC 是否解除静音"（旧清单编号），当前默认定向为 MCLK / SPK_EN / 功放硬件。
